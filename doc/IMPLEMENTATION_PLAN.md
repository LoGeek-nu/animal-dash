# 手描きキャラクター・2Dレースゲーム モック実装計画

- 文書バージョン: 0.1
- 作成日: 2026-08-19
- 対象: 学園祭・展示イベント向けゲームモック
- 配置先: Cloudflare
- 参照資料: [桜麗祭会議 tldraw](https://www.tldraw.com/f/dBqeUHGTXB3dYqQoKP2zC)

## 1. 目的

来場者が描いたキャラクターを使って、最大4人で参加できる横スクロール型2Dレースゲームの体験を検証する。

今回のモックではAIによるキャラクター生成、紙からの画像読み取り、画像切り抜きは実装しない。あらかじめ「生成済みキャラクター」として登録した画像を管理画面から選択し、メイン画面のキャラクター待機画面へリアルタイムに反映する。

モックで検証する中心課題は次のとおり。

- 受付後の参加者を、スタッフが迷わずレーンへ登録できるか
- 選択したキャラクターがメイン画面へ即時反映されるか
- 4レーンのキャラクターが見やすく、ゲームとして盛り上がるか
- ジャンプと加速の2操作で子どもでも遊べるか
- レース終了後の順位、タイム、ランキング表示が分かりやすいか
- 混雑時でもスタッフ3～4人で運営できるか

## 2. 想定する来場者フロー

1. 受付
2. 紙にキャラクターを描く
3. スタッフが生成済みキャラクターを管理画面から選択する
4. メイン画面の参加待ち枠にキャラクターが表示される
5. 1～4人がそろったら、不足枠をBOTで補充する
6. 操作説明を受ける
7. レースに参加、または観戦する
8. リザルト画面で順位とタイムを確認する
9. 希望者へ紙の原画や画像データを返却する
10. サークル紹介を見て退出する

画像データの配布、QRコード発行、印刷は今回のモック対象外とし、将来拡張として扱う。

## 3. ゲーム全体のフロー

```text
キャラクター待機
    ↓ スタッフが開始
カウントダウン
    ↓
レース
    ↓ 全員ゴール、または制限時間到達
リザルト
    ↓ 90秒経過、またはスタッフがスキップ
キャラクター待機
```

アプリ内部では以下の状態を持つ。

| 状態 | 内容 |
| --- | --- |
| `WAITING` | キャラクター登録待ち |
| `COUNTDOWN` | レース開始前のカウントダウン |
| `RACING` | レース進行中 |
| `RESULTS` | 結果とランキングを表示中 |
| `RECOVERY` | 通信切断や不整合からの復旧待ち |

## 5. システム構成

Cloudflare上に、フロントエンド、API、リアルタイム同期、データベース、画像ストレージをまとめる。

```text
来場者向けメイン画面 /game
              │ WebSocket
              ▼
      Cloudflare Worker
              │
              ▼
    Durable Object: EventRoom
              ▲
              │ WebSocket
スタッフ用管理画面 /admin

Cloudflare Worker
├─ Static Assets: Reactアプリ配信
├─ API: キャラクター、結果、画像取得
├─ Durable Objects: 現在のセッションとリアルタイム同期
├─ D1: キャラクターメタデータ、レース結果、ランキング
└─ R2: キャラクター画像、将来の元画像
```

### 5.1 採用技術

| 領域 | 採用技術 | 用途 |
| --- | --- | --- |
| フロントエンド | React + TypeScript + Vite | `/game`と`/admin` |
| ゲーム描画 | Canvas 2D | 4レーン、キャラクター、背景、障害物 |
| APIルーティング | Cloudflare Worker + Hono | REST API、認証確認、入力検証 |
| 静的配信 | Workers Static Assets | HTML、CSS、JavaScript、固定素材 |
| リアルタイム同期 | Durable Objects + WebSocket Hibernation API | 管理画面とメイン画面の同期 |
| 一時状態 | Durable Object Storage | 現在のフェーズ、参加枠、タイマー |
| 永続データ | Cloudflare D1 | キャラクター、レース、順位 |
| 画像 | Cloudflare R2 | 生成済みキャラクター画像 |
| テスト | Vitest + Playwright | 単体、結合、E2E |
| デプロイ | Wrangler | ローカル、ステージング、本番 |

### 5.2 Workers Static Assetsを選ぶ理由

今回のアプリは単なる静的サイトではなく、SPA、API、WebSocketを同じドメインで扱う。Workers Static Assetsを利用すると、Reactの静的ファイルとWorker APIを1回のデプロイで管理できる。

静的ファイルはCloudflareから直接配信し、`/api/*`と`/ws/*`だけWorkerを先に実行する。これにより不要なWorker呼び出しを減らす。

### 5.3 Durable Objectsを選ぶ理由

管理画面とメイン画面は、同じイベントセッションの状態を共有する必要がある。イベントIDごとにDurable Objectを1つ作り、単一の状態管理主体とする。

例:

```text
eventId: oureisai-2026
Durable Object: EventRoom("oureisai-2026")
```

Durable Objectが担当するもの:

- 現在のフェーズ
- 1～4番レーンの参加キャラクター
- BOTかどうか
- コースシード
- レース開始時刻
- 接続中の管理画面、メイン画面
- リザルト表示終了予定時刻
- 90秒後の自動リセット用Alarm

Durable Objectは休止時にメモリ上の値を失うため、重要な現在状態はDurable Object Storageへ逐次保存する。

### 5.4 D1とDurable Object Storageの使い分け

| データ | 保存先 | 理由 |
| --- | --- | --- |
| 現在の参加枠 | Durable Object Storage | 即時同期と強い整合性が必要 |
| 現在のフェーズ | Durable Object Storage | WebSocket接続者全員で共有 |
| 90秒タイマー | Durable Object Alarm | 再起動後も確実に実行するため |
| キャラクター一覧 | D1 | 管理画面で検索、並べ替えするため |
| 過去のレース | D1 | 履歴、TOP3集計に使用 |
| 順位、タイム | D1 | 永続的な記録として保持 |
| 画像本体 | R2 | バイナリをD1へ保存しないため |

## 7. メイン画面仕様

### 7.1 共通仕様

- 基準解像度は1920×1080、16:9とする
- Chrome最新版のフルスクリーン表示を主対象とする
- 観客が離れた位置から見ても読める文字サイズにする
- 画面の右上などに通信状態を小さく表示する
- 素材読み込み失敗時はプレースホルダー画像を表示する
- ESCなどの誤操作で画面が崩れないようにする

### 7.2 キャラクター待機画面

必要な表示:

- 1～4番の参加枠
- レーン色
- キャラクター画像
- 表示名
- スピード、加速、ジャンプ、スタミナなどの簡易ステータス
- 「参加者を待っています」の未登録表示
- 現在の登録人数
- 操作方法
- コースプレビュー、またはTIPS
- スタッフ操作待ちメッセージ

アニメーション:

- キャラクターの上下動
- 小さなジャンプ
- 左右の揺れ
- 登録時の登場演出
- 解除時の退場演出

将来拡張として、元の手描きイラストと生成後画像のビフォーアフター表示領域を確保する。

### 7.3 カウントダウン画面

- `3 → 2 → 1 → GO!`を中央へ大きく表示する
- 効果音を再生する
- カウントダウン中は操作を受け付けない
- 全キャラクターと障害物素材の読み込み完了後に開始する
- 読み込み失敗時は管理画面へエラーを通知する

### 7.4 レース画面

#### レイアウト

- 画面を縦方向へ最大4分割する
- 1レーンあたり画面高の約25%を使用する
- 各レーンにキャラクター画像、名前、レーン色、順位、スタミナを表示する
- レーンごとに独立した横スクロールを行う
- キャラクターは通常、画面左から25～30%付近に維持する
- ゴール直前では背景スクロールを停止し、キャラクター自身をゴールへ移動させる

#### 基本ルール

- 参加数は1～4人
- 人数不足時は管理画面からBOTを追加する
- レース時間の目安は45～60秒
- 制限時間を超えたキャラクターはDNFとして扱う
- 全レーンは同じコースシードと障害物配置を使用する
- レース開始後の途中参加とキャラクター入れ替えは禁止する

#### 操作

- ボタン1: ジャンプ
- ボタン2: 加速
- 加速中はスタミナを消費する
- 加速をやめるとスタミナが徐々に回復する
- スタミナが0になると一定量回復するまで加速できない
- モックではGamepad APIを優先し、キーボードを予備入力とする

入力処理はゲームロジックから分離し、次の入力元を同じインターフェースで扱えるようにする。

```text
InputProvider
├─ GamepadInputProvider
├─ KeyboardInputProvider
└─ 将来: SmartphoneInputProvider
```

#### キャラクターステータス

モックでは次の4項目を使用する。

| 項目 | 効果 |
| --- | --- |
| `speed` | 通常時の最大速度 |
| `acceleration` | 最大速度へ到達する速さ |
| `jump` | ジャンプの高さ |
| `stamina` | 加速可能時間と回復性能 |

極端な性能差で勝敗が決まらないよう、値の差は小さく制限する。AI評価を実装するまでは、管理画面で用意したプリセットから選択する。

#### 障害物

MVPでは2～3種類に限定する。

- 小さい障害物: ジャンプで回避可能
- 大きい障害物: 早めのジャンプが必要
- 減速地帯: 一時的に速度が落ちる

衝突時は短時間減速し、キャラクターを点滅または跳ね返す。操作不能時間は短くし、子どもが遊び続けられる設計にする。

#### スクロール

レーンごとに次の計算を行う。

```text
cameraX = clamp(
  playerX - viewportWidth * 0.28,
  0,
  courseLength - viewportWidth
)
```

コース終盤の一定位置から`cameraX`を固定し、キャラクターがゴールラインへ近づく演出に切り替える。

#### レース終了

- ゴールライン通過時刻をミリ秒で記録する
- 同着時は内部タイムの小さい順とする
- ゴール済みキャラクターは停止または喜ぶアニメーションを行う
- 全員ゴール後に1～2秒の間を置いてリザルトへ移動する
- 制限時間到達時は未ゴールをDNFとしてリザルトへ移動する

### 7.5 リザルト画面

画面左側:

- 開催日ごとのTOP3
- キャラクター画像
- 名前
- ベストタイム

画面右側:

- 今回の1～4位
- キャラクター画像
- 名前
- 順位
- ゴールタイム、またはDNF

画面下部:

- 「また遊んでね」メッセージ
- 待機画面へ戻るまでの残り時間
- サークル紹介への誘導

90秒経過後、Durable ObjectのAlarmで待機状態へ戻す。管理画面から即時スキップも可能とする。

## 8. 管理画面仕様

### 8.1 基本レイアウト

PCまたはタブレットから操作する。

```text
┌──────────────────────────────┐
│ 接続状態 / 現在フェーズ / イベントID │
├──────────────┬───────────────┤
│ キャラクター一覧 │ レーン1～4       │
│ 検索・選択       │ 割当・解除・BOT   │
├──────────────┴───────────────┤
│ 開始 / スキップ / リセット / 履歴   │
└──────────────────────────────┘
```

### 8.2 キャラクター操作

- 登録済みキャラクターをカード一覧で表示する
- 名前で検索できる
- 使用済み、未使用を確認できる
- キャラクターをレーン1～4へ割り当てる
- 既存キャラクターを別レーンへ移動する
- 解除する
- 表示名を修正する
- ステータスプリセットを変更する
- BOTを追加する
- レース中は割り当て操作を無効化する

### 8.3 進行操作

- `レース開始`
- `不足枠をBOTで補充して開始`
- `リザルトをスキップ`
- `待機画面へ戻す`
- `レースを強制終了`
- `直前の状態を再送信`

破壊的な操作には確認ダイアログを表示する。ただし会場運営を止めないよう、確認回数は最小限にする。

### 8.4 ステータス表示

- メイン画面の接続有無
- 管理画面自身の接続状態
- 最終同期時刻
- 現在のフェーズ
- セッションID
- 現在の参加者数
- 画像読み込みエラー
- D1への結果保存状態
- 自動リセット予定時刻

## 9. リアルタイム通信仕様

### 9.1 メッセージ共通形式

```json
{
  "type": "session.updated",
  "version": 1,
  "eventId": "oureisai-2026",
  "sessionId": "session_xxx",
  "sequence": 42,
  "sentAt": "2026-08-19T10:00:00.000Z",
  "payload": {}
}
```

`sequence`を使い、再接続時や通信遅延時に古い更新を適用しないようにする。

### 9.2 クライアントから送信する主なイベント

| イベント | 送信元 | 内容 |
| --- | --- | --- |
| `admin.assignCharacter` | 管理画面 | キャラクターをレーンへ割り当てる |
| `admin.removeCharacter` | 管理画面 | レーンから解除する |
| `admin.fillBots` | 管理画面 | 空きレーンをBOTで補充する |
| `admin.startRace` | 管理画面 | レース開始を要求する |
| `admin.skipResults` | 管理画面 | リザルトを終了する |
| `admin.resetSession` | 管理画面 | 待機状態へ強制リセットする |
| `game.ready` | メイン画面 | 素材読み込みと入力準備完了 |
| `game.raceStarted` | メイン画面 | ローカルレース開始を通知する |
| `game.raceFinished` | メイン画面 | 順位とタイムを送信する |
| `client.requestSnapshot` | 両画面 | 最新状態全体を要求する |

### 9.3 サーバーから配信する主なイベント

| イベント | 内容 |
| --- | --- |
| `session.snapshot` | 最新状態全体 |
| `session.updated` | レーンや参加者の変更 |
| `race.countdown` | カウントダウン開始 |
| `race.started` | レース開始確定 |
| `race.results` | 結果確定 |
| `session.reset` | 待機状態へ戻る |
| `server.warning` | 復旧可能な警告 |
| `server.error` | 操作失敗、保存失敗 |

### 9.4 ゲーム中に送らないもの

キャラクターの座標、速度、ジャンプ位置を毎フレームCloudflareへ送らない。ゲームループはメイン画面で実行し、サーバー通信は開始、終了、リセットなどの低頻度イベントに限定する。

これにより、会場ネットワークの遅延がレース操作へ直接影響しない構成にする。

## 10. ゲームループ設計

Canvas描画と物理更新は`requestAnimationFrame`で実行する。端末性能による速度差を避けるため、更新処理は固定タイムステップにする。

```text
Input
  ↓
Fixed Update
├─ 加速、減速
├─ スタミナ
├─ ジャンプ、重力
├─ 障害物衝突
├─ ゴール判定
└─ 順位計算
  ↓
Render
├─ 各レーンのカメラ位置
├─ 背景
├─ 障害物
├─ キャラクター
└─ UI
```

コースは`courseSeed`から生成し、リロードやテストで同じ配置を再現できるようにする。

| カラム | 型 | 内容 |

主なインデックス:

- `race_sessions(event_id, started_at)`
- `race_entries(race_session_id)`
- `race_entries(character_id)`
- `characters(enabled, created_at)`

### 11.2 R2キー設計

```text
characters/{characterId}/generated.png
characters/{characterId}/source.png
characters/{characterId}/thumbnail.webp
```

画像の公開範囲を制御できるよう、R2バケットは原則非公開とし、Workerの`/api/media/:key`経由で返す。

モック開始時は、サンプルキャラクター10体程度をR2とD1へ投入するシード処理を用意する。

## 12. API設計

| Method | Path | 用途 |
| --- | --- | --- |
| GET | `/api/characters` | 利用可能なキャラクター一覧 |
| GET | `/api/characters/:id` | キャラクター詳細 |
| PATCH | `/api/characters/:id` | 表示名、ステータス修正 |
| GET | `/api/rankings?eventId=...&date=...` | 日別TOP3 |
| GET | `/api/races/:id` | レース結果詳細 |
| GET | `/api/media/:key` | R2画像取得 |
| GET | `/health` | ヘルスチェック |

参加枠の変更、開始、リセットはWebSocketを通じてDurable Objectへ送る。REST APIとWebSocketの双方で入力値を検証する。

## 13. Cloudflare環境設計

### 13.1 環境

| 環境 | 用途 | 例 |
| --- | --- | --- |
| Local | 開発 | `wrangler dev` |
| Staging | 実機確認、レビュー | `race-stg.example.com` |
| Production | 当日運用 | `race.example.com` |

D1、R2、Durable Objectの名前空間はステージングと本番で分離する。

例:

```text

├─ character-race-db-staging
└─ character-race-db-production

R2
├─ character-race-images-staging
└─ character-race-images-production
```

### 13.2 Wrangler設定方針

- `compatibility_date`を固定し、定期的に更新する
- 静的ファイル用`assets` bindingを設定する
- D1 bindingを設定する
- R2 bindingを設定する
- Durable Object bindingとSQLite migrationを設定する
- `/api/*`と`/ws/*`だけWorker-first routingにする
- ステージングと本番の環境変数を分離する
- 秘密情報はコードやGitへ置かず、Worker Secretで管理する
- binding変更後は型定義を再生成する

### 13.3 デプロイ手順

1. Cloudflareプロジェクトを作成する
2. ローカルでReact SPAとWorkerを起動する
3. D1データベースを作成する
4. D1 migrationをローカルへ適用する
5. R2バケットを作成する
6. Durable Object namespaceとmigrationを設定する
7. サンプルキャラクターを投入する
8. ステージングへデプロイする
9. ステージングで管理画面とメイン画面を別端末から確認する
10. D1 migrationを本番へ適用する
11. 本番Workerへデプロイする
12. 独自ドメイン、または`workers.dev` URLで公開する
13. `/admin`のアクセス制限を確認する
14. ログとUsageを確認する

本番デプロイでは、D1 migrationを先に適用し、その後に互換性のあるWorkerをデプロイする。破壊的なmigrationは避け、カラム追加などの後方互換性がある変更を基本とする。

## 14. 認証、セキュリティ、プライバシー

### 14.1 管理画面

- `/admin`はCloudflare Accessなどでスタッフだけに制限する
- 管理操作APIも画面の表示制限とは別に認可確認する
- ステージングと本番で認証設定を分離する
- 管理操作は監査用に時刻、操作種別、セッションIDをログへ残す

### 14.2 メイン画面

- `/game`を一般公開するか、イベント端末だけに限定するかを本番前に決定する
- 公開する場合も、状態変更APIは利用できないようにする
- 推測可能なURLだけを管理権限の代わりにしない

### 14.3 画像と参加者情報

- 本名ではなくニックネームを使用する
- 画像に個人情報が含まれないかスタッフが確認する
- R2キーを直接自由入力させない
- 取得可能な画像形式と最大サイズを制限する
- Content-Typeを検証する
- 画像保存期間と削除方法を決める
- データ配布機能を追加する場合は、他人の画像を取得できない設計にする

## 15. 通信切断と復旧

### 15.1 WebSocket再接続

- 指数バックオフで自動再接続する
- 接続成功時に`session.snapshot`を必ず取得する
- `sequence`が古いイベントは破棄する
- 管理画面へ最終同期時刻を表示する
- 5秒以上切断した場合は画面上へ警告する

### 15.2 状態復旧

- `WAITING`と`RESULTS`はDurable Objectの状態から完全復旧する
- `RACING`中はメイン画面の`localStorage`へ低頻度でチェックポイントを保存する
- チェックポイントの整合性が取れない場合は`RECOVERY`へ入り、管理画面から再開またはリセットする
- レース結果のD1保存に失敗した場合は再試行し、二重登録を防ぐためセッションIDを一意キーとして扱う

### 15.3 インターネット回線断

ゲーム計算はメイン画面内で行うため、進行中のレースは通信が切れても最後まで動かせる設計にする。結果は接続回復後に送信する。

ただし、Cloudflareへ完全に接続できない間は、別端末の管理画面から新しいキャラクターを同期できない。完全オフライン運用が必須になった場合は、会場LAN内のローカルサーバーまたは別の直接通信方式を追加する必要があり、MVP外とする。

## 21. 主なリスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| AI部分とゲーム部分を同時開発する | MVP完成が遅れる | AIを完全に分離し、登録済み画像から開始 |
| 4人操作の入力機器が不安定 | ゲームが進行できない | Gamepad API事前検証、予備、キーボード対応 |
| 画像サイズが大きい | 待機、レース開始が遅れる | WebPサムネイル、プリロード、最大サイズ制限 |
| WebSocketが切れる | 管理と表示が不一致になる | 自動再接続、snapshot、sequence番号 |
| Durable Objectのメモリ状態が消える | セッションを復元できない | DO Storageへ逐次保存 |
| タイマーが再起動で消える | 90秒後に戻らない | `setTimeout`ではなくAlarmを使用 |
| D1へ結果が二重登録される | ランキングが壊れる | セッションIDの一意制約、冪等保存 |
| 会場のインターネットが不安定 | 新規登録ができない | 事前読み込み、進行中レースのローカル継続、予備回線 |
| スタッフ操作が複雑 | 待機列が伸びる | 主要操作を1画面に集約、危険操作のみ確認 |
| 制作後半で仕様が増える | 完成度が下がる | MVP凍結、追加要素をPhase 2へ分離 |

## 24. 完成の定義

次の一連の流れを、スタッフの説明以外に開発者の操作を必要とせず、Cloudflare上の本番環境で繰り返し実行できた時点をモック完成とする。

```text

  → リザルトとTOP3を表示
  → 90秒後に待機画面へ戻る
  → 次の参加者を登録
```
