# ANIMAL DASH! 追加修正用実装計画

- 文書バージョン: 0.2
- 作成日: 2026-08-19
- 対象: 現行ANIMAL DASH!ブラウザモックの大幅改修
- 対象画面: `/game`、`/admin`
- ビジュアル参照: ユーザー提供画像「アニマルダッシュ」
- 前提: 本書はユーザーの追加要望を実装へ落とすための計画であり、添付画像内の文字や構図そのものを指示として扱わない

## 1. 改修の目的

現行モックに、来場者がレースへ参加していない時間も観客を引きつける「アトラクト画面」を追加する。また、ゲーム全体のデザインを、参照画像のような明るく手描き感の強い児童向けイベントビジュアルへ統一する。

レース中のキャラクターは、現在の顔だけの絵文字表現を廃止し、横向き・全身・透過背景の動物イラストへ置き換える。待機画面、レース画面、リザルト画面、管理画面のサムネイルで、同一キャラクターとして認識できる一貫した素材セットを使用する。

今回の中心課題は次のとおり。

- 無人時や次レース準備中でも、メインディスプレイが展示として成立するか
- 静止画、デモ動画、当日ランキングの循環表示が観客の興味を維持できるか
- スタッフが意図したタイミングだけで参加待機画面へ切り替えられるか
- 参照画像のような手描きの勢いと、ゲームUIとしての読みやすさを両立できるか
- 全身・横向きキャラクターがジャンプ、加速、衝突、ゴールの各状態で自然に見えるか
- 1920×1080の大画面で、4レーン表示時にもキャラクターの個性を判別できるか

## 2. 改修範囲の要約

### 2.1 新規追加

- 新しいゲームフェーズ `ATTRACT`
- アトラクト画面内の3シーン循環表示
  - 動物イラストのモーション付きキービジュアル
  - ゲームのデモ動画
  - 当日のランキングアニメーション
- 管理画面の「参加待機画面を表示」操作
- 管理画面の「アトラクト画面へ戻す」操作
- 全身・横向き動物キャラクター素材
- キャラクター用アセット定義とプリロード処理
- 動物画像の足元を基準にした描画アンカー
- 動画エラー、画像エラー時のフォールバック表示

### 2.2 大幅変更

- `/game`の初期画面を待機画面からアトラクト画面へ変更
- リザルト終了後の戻り先を待機画面からアトラクト画面へ変更
- ゲーム画面、待機画面、リザルト画面のビジュアルを全面改修
- 絵文字ベースの顔アイコンを生成済みイラストへ置換
- 管理画面のフェーズ操作とキャラクターサムネイルを更新
- レース中のキャラクター描画サイズ、当たり判定基準、ジャンプ基準を調整

### 2.3 今回も対象外とするもの

- 来場者が描いた紙からの画像読み取り
- AIによる当日のキャラクター自動生成
- 生成画像の自動背景除去パイプライン
- スマートフォンコントローラー
- 本番用D1、R2、Durable Objectsへの完全移行
- ライブ配信や外部動画配信サービスへの依存

## 3. 参照画像から抽出するデザインルール

参照画像をそのまま背景として使うのではなく、以下の視覚的特徴をデザインシステムへ分解して各画面へ反映する。

### 3.1 色

- 空色を画面全体の基調色にする
- 赤、橙、黄、緑、青、紫、桃色を高彩度のアクセントとして使う
- UI文字には濃紺または焦げ茶を使い、真っ黒は最小限にする
- パネルは白または生成りの紙色にし、背景から明確に浮かせる
- レーン色は現在の4色を維持しつつ、クレヨンや絵の具のムラを加える

暫定カラートークン:

| 用途 | 暫定値 |
| --- | --- |
| 空 | `#35BDF4` |
| 紙 | `#FFF9E8` |
| 輪郭 | `#3B2A2A` |
| 赤 | `#F0443E` |
| 黄 | `#FFBF1F` |
| 緑 | `#3CB53C` |
| 青 | `#218CE0` |
| 紫 | `#8734D7` |
| 桃 | `#F24BA8` |

### 3.2 線と質感

- 均一なベクター線ではなく、太さが少し揺れる濃色の輪郭線を使う
- キャラクターと主要な見出しには、太い白縁と薄い落ち影を付ける
- 背景に水彩、クレヨン、色鉛筆、紙の繊維に近いテクスチャを重ねる
- パネルやボタンは完全な長方形ではなく、少し不均一な角丸や傾きを使う
- 紙吹雪、星、集中線、足元の砂煙など、動きを補強する小さな装飾を配置する
- テクスチャは可読性を損なわない濃度に固定し、文字の背面は比較的フラットにする

### 3.3 タイポグラフィ

- メインタイトルは太く、丸く、色ごとに塗り分けた手描き風の表現にする
- タイトルや日本語の重要語はHTML/CSSで描画し、生成画像内の文字にはしない
- 生成AIによる文字崩れを避けるため、画像素材には原則として文字を含めない
- 本文とステータスは丸ゴシック系で統一し、大画面から読める太さを確保する
- 数字、順位、タイムは形が崩れないフォントを使用し、アニメーション中も読み取れるようにする

### 3.4 構図

- キャラクターは画面の主役として大きく見せる
- 画面奥から手前へ飛び出すような遠近感、集中線、砂煙を使う
- レースゲート、チェッカーフラッグ、三角旗、紙吹雪を共通モチーフにする
- UI情報を増やしすぎず、キャラクターとゲーム状態を最初に認識できる構図にする

## 4. 新しい全体フロー

```text
アトラクト画面 ATTRACT
├─ キービジュアル
├─ デモ動画
└─ 当日ランキング
    ↑ 3シーンを自動循環
    │
    └─ 管理画面「参加待機画面を表示」
                  ↓
キャラクター待機 WAITING
                  ↓ 管理画面「レース開始」
カウントダウン COUNTDOWN
                  ↓
レース RACING
                  ↓
リザルト RESULTS
                  ↓ 90秒経過、または管理画面でスキップ
アトラクト画面 ATTRACT
```

重要な変更点:

- アプリ起動直後は必ず `ATTRACT` とする
- `ATTRACT`から`WAITING`への遷移は管理画面操作だけで行う
- アトラクト画面の3シーン切り替えはゲーム画面内のローカルタイマーで行う
- 管理画面は現在どのアトラクトシーンを表示中か確認できる
- `RESULTS`終了後は自動で`ATTRACT`へ戻し、次のレース準備中も展示を継続する
- `ATTRACT`と`WAITING`ではキャラクター割り当てを許可する
- `COUNTDOWN`以降は現在と同様、割り当てと解除を禁止する

## 5. 状態設計の変更

### 5.1 RacePhase

```ts
type RacePhase =
  | "ATTRACT"
  | "WAITING"
  | "COUNTDOWN"
  | "RACING"
  | "RESULTS"
  | "RECOVERY";
```

### 5.2 アトラクト画面内のローカル状態

```ts
type AttractScene = "HERO" | "DEMO" | "RANKING";

type AttractPlayback = {
  scene: AttractScene;
  startedAt: number;
  paused: boolean;
};
```

`AttractPlayback`は画面演出用の状態であり、毎フレーム共有状態へ保存しない。管理画面には低頻度でシーン名だけを通知するか、デモモックではゲーム画面側の表示目安として扱う。

### 5.3 新しい操作

| 操作 | 条件 | 結果 |
| --- | --- | --- |
| `showWaitingScreen` | `ATTRACT` | `WAITING`へ遷移 |
| `showAttractScreen` | `ATTRACT`、`WAITING`、`RESULTS` | `ATTRACT`へ遷移 |
| `restartAttractLoop` | `ATTRACT` | `HERO`から再生 |
| `startRace` | `WAITING`かつ参加者1名以上 | `COUNTDOWN`へ遷移 |
| `skipResults` | `RESULTS` | `ATTRACT`へ遷移 |

### 5.4 初期状態とリセット

- `createInitialSession()`の初期フェーズを`ATTRACT`にする
- 通常リセットは参加枠をクリアし、`ATTRACT`へ戻す
- 「参加枠を維持してアトラクトへ戻す」と「すべてクリアして戻す」は管理画面で分ける
- リザルトの自動タイマー完了時は参加枠をクリアして`ATTRACT`へ戻す

## 6. アトラクト画面仕様

### 6.1 共通仕様

- 1920×1080、16:9を基準にする
- 3シーンを自動で繰り返す
- シーン切り替え時に真っ黒なフレームを出さない
- 右上に接続状態を小さく表示する
- 画面下部へ常時「スタッフ受付中」「次のレース準備中」などの短い案内を表示できる
- `prefers-reduced-motion`では移動量を減らし、フェード中心に切り替える

暫定再生時間:

| シーン | 時間 | 内容 |
| --- | ---: | --- |
| `HERO` | 12秒 | 動物キービジュアルと軽いモーション |
| `DEMO` | 24秒 | ゲームのデモ動画 |
| `RANKING` | 14秒 | 当日ランキングのアニメーション |

合計50秒で1周し、スタッフ操作がなければ連続再生する。

### 6.2 HERO: モーション付きキービジュアル

参照画像のような、動物がレースゲートから飛び出す1枚絵を基本にする。ただし画面全体を単純に拡大縮小するだけではなく、主要要素をレイヤー分けして軽く動かす。

レイヤー例:

1. 空、水彩テクスチャ
2. レースゲート、旗、観客席
3. 紙吹雪、星、集中線
4. 奥側の動物
5. 手前の動物
6. タイトル、開催案内

モーション:

- 動物ごとに1～3%の上下動と微小な回転
- 手前の動物だけ少し大きく動かして奥行きを出す
- 紙吹雪をゆっくり落下させる
- 集中線を周期的に伸縮させる
- タイトルを初回だけ小さく弾ませる
- 12秒間で背景を最大3%だけパンする

避けるもの:

- 画面全体の激しい揺れ
- 連続する大きなズーム
- キャラクターの顔や体をCSSで不自然に変形する演出
- 読みづらい量の紙吹雪

### 6.3 DEMO: ゲームデモ動画

- 20～24秒程度の短いレース紹介動画を使用する
- 内容は「待機画面 → カウントダウン → ジャンプ → 加速 → ゴール → リザルト」の要点を含める
- 音声は初期状態でミュートし、ブラウザの自動再生制限を回避する
- `autoplay muted playsInline`を設定する
- 操作UIと動画コントロールは表示しない
- 動画終了、または設定時間到達でランキングへ移動する
- 動画読込失敗時は、レース画面の静止画3枚をクロスフェードするフォールバックへ切り替える

暫定ファイル仕様:

| 項目 | 値 |
| --- | --- |
| 解像度 | 1920×1080 |
| 形式 | MP4 H.264 + poster WebP |
| フレームレート | 30fps |
| 音声 | なし、または無音トラック |
| 目標容量 | 15MB以下 |
| パス | `/media/animal-dash-demo.mp4` |

### 6.4 RANKING: 当日ランキング

- 当日のTOP10を表示し、最低でもTOP3はキャラクター画像付きで大きく見せる
- 画面開始時はランキングカードを画面下に待機させる
- 10位から順に、下から上へ勢いよく登場させる
- TOP3は最後に大きく表示し、1位へ冠と紙吹雪を付ける
- 登場は100～140ms間隔のstagger animationとする
- オーバーシュートするイージングを使い、「ばーっと上がる」印象を作る
- 全件表示後に8秒程度静止し、内容を読める時間を確保する

モック時のデータ:

- `localStorage`内の当日レース結果と既存サンプルランキングを統合する
- レース結果がない場合はサンプルランキングを表示する
- ランキングシーンへ入る直前に再集計する

本実装時のデータ:

- `/api/rankings?eventId=oureisai-2026&date=2026-08-19&limit=10`から取得する
- D1集計結果を利用する
- 通信失敗時は最後に成功したランキングを保持する

## 7. 管理画面の追加仕様

### 7.1 フェーズ操作

管理画面へ以下を追加する。

- `参加待機画面を表示`
- `アトラクト画面へ戻す`
- `アトラクトを最初から再生`
- 現在のアトラクトシーン表示
- 次のシーンまでのおおよその残り時間

主要ボタンの表示条件:

| 現在フェーズ | 主ボタン |
| --- | --- |
| `ATTRACT` | `参加待機画面を表示` |
| `WAITING` | `レース開始`、`アトラクトへ戻す` |
| `COUNTDOWN` | `強制終了` |
| `RACING` | `強制終了` |
| `RESULTS` | `リザルトを終了してアトラクトへ` |

### 7.2 運営フロー

推奨運用:

1. メイン画面はアトラクト表示を続ける
2. スタッフは管理画面で参加者をレーンへ事前登録する
3. 説明開始時に「参加待機画面を表示」を押す
4. 来場者が自分のキャラクターと操作を確認する
5. 「レース開始」を押す
6. リザルト終了後は自動でアトラクトへ戻る

`ATTRACT`中のキャラクター割り当てを許可することで、メイン画面の展示を止めずに次レースを準備できる。

### 7.3 確認ダイアログ

- レース中にアトラクトへ戻す場合だけ確認する
- `WAITING`から`ATTRACT`へ戻る場合は、参加枠を維持するかクリアするか選択させる
- 通常の`ATTRACT → WAITING`は確認なしで即時反映する

## 8. 全身・横向きキャラクター素材計画

### 8.1 基本方針

現在の絵文字はすべて生成済みイラストへ置き換える。文字やUIと画像生成を混在させず、生成対象は動物キャラクターだけに限定する。

キャラクター共通条件:

- 右向きの横姿
- 頭だけでなく全身が入る
- 4本脚または腕・脚の走りが分かるポーズ
- 大きな目、丸い輪郭、短めの手足
- 元気で親しみやすい表情
- 太く少し揺れる濃茶の輪郭線
- クレヨン、水彩、色鉛筆の混ざった手描き質感
- 白いステッカー縁は素材側に入れず、必要に応じてCSSまたは書き出し工程で統一する
- 背景は完全透過
- 影、文字、ロゴ、地面、紙吹雪を素材へ含めない
- すべて同じ向き、基準線、縮尺で作る

### 8.2 対象キャラクター

現行10体を維持する。

1. ももラビ: 白いうさぎ
2. トラまる: オレンジのトラ猫
3. けろっぴん: ミントグリーンのカエル
4. ぱんこぐま: はちみつ色のクマ
5. こんこん: オレンジのキツネ
6. ぺんた: 青系のペンギン
7. コロすけ: 茶色の子犬
8. あずき: 紫アクセントの猫
9. どらみん: 緑の子ドラゴン
10. ふわりん: 白と桃色のヒツジ

### 8.3 1体あたりの素材

| ファイル | 用途 | 向き |
| --- | --- | --- |
| `portrait.webp` | 待機、管理、リザルト | 正面寄りの3/4、全身 |
| `run-a.webp` | 走行フレームA | 右向き |
| `run-b.webp` | 走行フレームB | 右向き |
| `jump.webp` | ジャンプ | 右向き |
| `hit.webp` | 障害物衝突 | 右向き |
| `goal.webp` | ゴール、喜び | 右向きまたは3/4 |

合計60点を最終セットとする。ただし初回実装では、4体分を先行生成して画面サイズと動きを確定し、その後10体へ展開する。

### 8.4 生成手順

1. 10体のキャラクター設定表を固定する
2. 各キャラクターの`portrait`を生成し、色、顔、装飾を承認する
3. 承認済み`portrait`を同一性の参照画像として各ポーズを生成する
4. 全キャラクターを同じ右向き、同じキャンバス比率へ揃える
5. 背景透過、余白、足元基準を検査する
6. マスターPNGから表示用WebPを作る
7. 実ゲームへ4体を入れ、サイズと2フレーム走行を検証する
8. 残り6体へ展開する

生成時は、毎回次の不変条件を明記する。

- 顔、模様、体色、首輪・バンダナなどの識別要素を変えない
- 右向きを維持する
- 全身を切らない
- 透明背景を維持する
- 文字を追加しない
- 参照画像の手描きテイストを維持する

### 8.5 ファイル構成

```text
public/
└─ characters/
   ├─ momo/
   │  ├─ portrait.webp
   │  ├─ run-a.webp
   │  ├─ run-b.webp
   │  ├─ jump.webp
   │  ├─ hit.webp
   │  └─ goal.webp
   ├─ toramaru/
   └─ ...
```

マスターPNGは制作データとして`assets/source/characters/`へ保持し、ブラウザ配信対象から外す。

### 8.6 描画メタデータ

画像サイズだけで位置を決めず、キャラクターごとに基準値を持つ。

```ts
type CharacterRenderMeta = {
  width: number;
  height: number;
  footAnchorX: number;
  footAnchorY: number;
  hitboxWidth: number;
  hitboxHeight: number;
  visualScale: number;
};
```

- `footAnchor`を地面とジャンプ計算の基準にする
- 当たり判定は画像全体ではなく、胴体と足元を中心とした矩形にする
- 耳、しっぽ、羽などは当たり判定へ含めない
- 見た目の大きさが異なる動物も、ゲーム上の当たり判定は大きく変えない

## 9. キャラクターアニメーション仕様

### 9.1 待機画面

- `portrait`を大きく表示する
- 呼吸するような1～2%の上下動
- 耳、しっぽ、手の小さな動きはCSSではなく、画像全体の回転と位置変化で控えめに表現する
- 登録時は下から弾んで登場する
- 解除時は紙吹雪を残して横へ退場する

### 9.2 レース画面

- 通常走行は`run-a`と`run-b`を8～12fps相当で交互表示する
- 加速中はフレーム間隔を短くし、後方へ速度線と砂煙を追加する
- ジャンプ中は`jump`へ切り替える
- 衝突中は`hit`へ切り替え、短時間点滅する
- ゴール後は`goal`へ切り替える
- 画像切替でレイアウトが動かないよう、全ポーズを同じキャンバスサイズへ揃える

### 9.3 リザルト画面

- 1位は`goal`を大きく表示する
- 2～4位も`goal`または`portrait`を使用する
- 表情とポーズを優先し、ステータス情報は待機画面より減らす

## 10. 画面ごとのスタイル変更

### 10.1 アトラクト画面

- 参照画像に最も近い密度と華やかさを持つ画面にする
- レースゲート、紙吹雪、集中線、大きなタイトルを使用する
- ただし画面下の運営案内は白い紙パネルに載せて読みやすくする

### 10.2 キャラクター待機画面

- 現在の均一なカード4枚を、白縁ステッカー風のキャラクター台座へ変更する
- キャラクター画像をカード面積の55～65%まで大きくする
- ステータスはクレヨンで塗ったゲージとして表示する
- 背景へ三角旗と小さな紙吹雪を追加する
- 空きレーンは破線カードではなく、スケッチブックの白紙ページ風にする
- 操作説明はゲームパッドの手描き風アイコンを使う

### 10.3 カウントダウン

- 数字を白縁・多色・手描き風にする
- キャラクターはスタート姿勢の横向き全身画像を表示する
- `GO!`で集中線と紙吹雪を短時間だけ強く表示する

### 10.4 レース画面

- 背景を水彩風の校庭、草地、空へ変更する
- 各レーンは同じコースだが、色付きの旗や路面ラインで識別する
- キャラクターを現在の顔アイコンより1.4～1.8倍大きくする
- UIはキャラクターを隠さないよう、名前と順位を左端、スタミナを右上へ整理する
- 障害物も手描きテイストの石、丸太、水たまりへ変更する
- 速度線、砂煙、衝突星を共通エフェクトとして用意する

### 10.5 リザルト

- 1位キャラクターを中央または上段へ大きく配置する
- 表彰台を赤白のレースゲートや旗で囲む
- タイムと順位は白いステッカー型パネルへ載せる
- TOP3と今回結果を1画面に詰め込みすぎず、視線順を明確にする

### 10.6 管理画面

- 運営画面は華やかさより操作性を優先し、現在の情報密度を維持する
- キャラクター画像だけを新しい`portrait`へ置換する
- フェーズボタンは色と文言を明確にする
- `ATTRACT`は青、`WAITING`は黄、`RACING`は緑、`RESULTS`は紫とする
- 破壊的操作だけ赤にする

## 11. コンポーネント構成の整理

現在の`app/AnimalDashApp.tsx`はゲーム画面と管理画面が同居しているため、本改修に合わせて分割する。

│  └─ components/
│     ├─ GameExperience.tsx
│     ├─ attract/
│     │  ├─ AttractScreen.tsx
│     │  ├─ HeroScene.tsx
│     │  ├─ DemoScene.tsx
│     │  └─ RankingScene.tsx

## 13. 素材読み込み

### 13.1 プリロード

- `ATTRACT`表示中に次レースで使うキャラクター素材を先読みする
- `WAITING`へ遷移した時点で`portrait`を読み込み済みにする
- `COUNTDOWN`開始前に`run-a`、`run-b`、`jump`、`hit`、`goal`の読込を確認する
- 読込完了前はレース開始ボタンを一時的に無効化する
- 管理画面へ「ゲーム素材準備OK」を表示する

### 13.2 フォールバック

- `portrait`失敗時は、同キャラクターの`run-a`を使用する
- レース用画像失敗時は、`portrait`を横移動させる簡易表示へ切り替える
- すべて失敗した場合は、名前入りの色付きシルエットを表示する
- 画像404でレース全体を停止しない

## 14. モーション設計

共通の時間とイージングを定義する。

| 名称 | 時間 | 用途 |
| --- | ---: | --- |
| `motion-fast` | 140ms | ボタン、選択 |
| `motion-base` | 280ms | カード登場、フェード |
| `motion-bounce` | 520ms | キャラクター、ランキング登場 |
| `motion-scene` | 700ms | アトラクトのシーン切替 |

ルール:

- 常に動く要素は一画面6種類以内にする
- 順位やタイムなど読む情報は、登場後に十分な静止時間を取る
- 点滅は短くし、1秒に3回を超えない
- `prefers-reduced-motion`ではランキングを一括フェード表示する

## 15. 音声

今回の必須範囲は無音でも成立させる。

追加する場合:

- アトラクト動画は初期ミュート
- HEROとRANKINGには常時音声を付けない
- カウントダウン、ジャンプ、加速、衝突、ゴールだけ効果音を使用する
- 管理画面に全体ミュート状態を表示する
- ページ読込直後の自動音声再生には依存しない

## 16. テスト計画

### 16.1 単体テスト

- 初期フェーズが`ATTRACT`になる
- `ATTRACT → WAITING`は管理操作だけで遷移する
- `WAITING → COUNTDOWN → RACING → RESULTS → ATTRACT`が成立する
- `ATTRACT`と`WAITING`ではキャラクター変更ができる
- `COUNTDOWN`以降は変更できない
- リザルトタイマー完了時に`ATTRACT`へ戻る
- ランキングが同一キャラクターの重複記録を正しく整理する
- 足元アンカーと当たり判定がキャラクターごとに適用される

### 16.2 コンポーネントテスト

- HERO、DEMO、RANKINGが設定時間で切り替わる
- 動画終了イベントで次シーンへ進む
- 動画エラー時に静止画フォールバックへ切り替わる
- ランキングカードが10位から順に登場する
- 画像404時に代替表示が出る
- 全身画像の読み込みでレイアウトが跳ねない

### 16.3 E2Eテスト

1. `/game`を開き、アトラクト画面を確認する
2. HEROからDEMO、RANKINGまで1周する
3. `/admin`で4体を割り当てる
4. 管理画面から参加待機画面へ遷移する
5. メイン画面に4体の全身キャラクターが表示される
6. レースを開始する
7. `run-a`と`run-b`が切り替わる
8. ジャンプ、加速、衝突表示を確認する
9. リザルトへ進む
10. スキップ操作でアトラクトへ戻す
11. ランキングシーンで今回の結果が反映される

追加ケース:

- 参加枠0名のまま`WAITING`を表示する
- `ATTRACT`中に参加者を登録する
- `WAITING`から参加枠を維持して`ATTRACT`へ戻す
- 動画ファイル404
- キャラクター画像1枚だけ404
- 10体すべての表示サイズ差
- 1920×1080、1366×768、タブレット幅
- `prefers-reduced-motion`

### 16.4 目視確認

- キャラクターの顔や模様が全ポーズで同じに見える
- 全キャラクターが右向きである
- 耳、しっぽ、足が切れていない
- 足元が同じ地面ラインに接している
- 4レーンでキャラクターの大きさが極端に違わない
- 背景が華やかでも名前、順位、スタミナが読める
- プロジェクター表示で暗部が潰れない

## 17. 性能目標

- レース中は60fpsを目標とし、最低45fpsを維持する
- 1キャラクター1ポーズあたりWebP 250KB以下を目安とする
- 次レース4体分の必須画像合計を5MB以下にする
- デモ動画を15MB以下にする
- `ATTRACT`中にレース素材をバックグラウンドで先読みする
- 画像切替時に追加レイアウト計算を発生させない
- 長時間のアトラクト再生でメモリ使用量が増え続けない

## 20. 主なリスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| ポーズごとに顔や模様が変わる | 同一キャラクターに見えない | 承認済みportraitを参照し、不変条件を固定して生成 |
| 横向きが左右混在する | レース方向が不自然 | 全素材を右向きで検品し、必要時だけCSS反転を明示 |
| 画像の足元や縮尺が揃わない | キャラクターが浮く、沈む | 共通キャンバスとfootAnchorを使用 |
| 60点生成で修正回数が増える | スケジュール遅延 | 4体先行で仕様を確定してから残りへ展開 |
| 背景と装飾が派手すぎる | UIが読めない | 文字は白い紙パネル上へ置き、装飾密度に上限を設ける |
| 動画が自動再生されない | DEMOが止まる | muted、playsInline、静止画フォールバック |
| 動画と画像が重い | 起動、レース開始が遅い | WebP、MP4圧縮、ATTRACT中プリロード |
| ランキングが古い | 展示内容の信頼性低下 | シーン開始時に再集計し、最終取得時刻を表示 |
| 長時間アニメーションでメモリが増える | 当日途中で停止 | タイマー解除、動画再利用、連続再生テスト |
| 全身画像で当たり判定が大きくなる | 遊びにくい | 画像全体ではなく共通の胴体ヒットボックスを使用 |

## 22. 完成の定義

次の流れを開発者の介入なしで繰り返せた時点を、追加修正の完成とする。

```text
アプリ起動
  → アトラクト画面でHERO・デモ動画・当日ランキングを循環
  → スタッフがアトラクト表示中に参加者を登録
  → 管理画面から参加待機画面を表示
  → 全身キャラクターと操作方法を確認
  → レース開始
  → 横向き全身キャラクターが走行・ジャンプ・加速
  → 順位とタイムを確定
  → 手描きテイストのリザルトを表示
  → 90秒後、またはスタッフ操作でアトラクトへ戻る
  → ランキングシーンへ今回結果が反映される
```

この状態で、参照画像のような「明るい、手描き、にぎやか、かわいい、勢いがある」という印象が全画面で一貫し、スタッフがアトラクト表示と参加受付を明確に切り替えられることを最終条件とする。
