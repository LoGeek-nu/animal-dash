# 管理画面のキャラクターサムネイル（Issue #88）

管理画面のキャラクター一覧・レーン・詳細・生成結果は、長辺256px以内・WebP品質80のサムネイルを表示します。縦横比と透過を維持し、小さい元画像は拡大しません。元画像のR2オブジェクト・D1の `image_key`・ゲーム画面の画像URLは変更しません。

| 用途 | R2キー | URL |
| --- | --- | --- |
| 元画像／ゲーム画面 | `characters/<id>.png`（実際のContent-Typeを保持） | `/api/characters/<id>/image` |
| 管理画面 | `thumbnails/v1/<id>.webp` | `/api/characters/<id>/thumbnail/v1` |

キーとURLはIDから決まるため、DBマイグレーションは不要です。R2の既存取り込み処理は `characters/` だけを対象とし、サムネイルを別キャラクターとして取り込みません。静的キャラクターは従来の画像を使います。

## 新規生成と画像取得

生成APIは元画像とD1の保存後に、Cloudflare Images bindingでサムネイルを変換・R2へ保存してから応答します。元画像をストリームで変換サービスへ渡し、小さい出力のみバッファー化して保存します。必要な `IMAGES` バインディングは本番設定・develop設定に定義しています。今回デプロイするのはdevelopのみです。

サムネイルだけ失敗した場合は構造化ログ `character_thumbnail_generation_failed` を残し、生成自体は成功として返します。再生成によるキャラクター重複を防ぐためです。サムネイルがない・R2読み取りが失敗した場合は、GETが元画像へ307リダイレクトします。このリダイレクトは `no-store` で、後から補完したサムネイルを使えるようにします。恒常的な変換失敗時は下記スクリプトを再実行してください。

公開のGET/HEADでは変換処理もR2書き込みも実行しません。変換は新規生成時とスタッフ専用POSTだけです。サムネイルはR2から返し、今回追加のCDN Cache APIは使いません。ブラウザには元画像と同様 `public, max-age=31536000, immutable` を返します。仕様変更時はキー／URLのバージョンを上げ、既存URLの画像を上書きしないでください。

## 既存画像の補完

```bash
node scripts/backfill-character-thumbnails.mjs \
  https://animaldash-develop.logeek.tech \
  /absolute/path/to/develop-passcode.txt \
  outputs/thumbnail-backfill.json \
  写真テスト 2
```

- 合言葉は保護されたファイルから読み込み、コマンド引数・レポートへ値を出しません。
- 第4引数は検索文字列です。省略または空文字 `''` で検証環境の生成キャラクターすべてが対象です。静的キャラクターは対象外です。
- 一覧APIを12件ずつページングし、同時処理数1〜4（既定2）でIDごとのスタッフ専用POSTを実行します。最初の1件を事前確認してから並列処理します。
- 既存サムネイルはスキップします。失敗時は1秒・2秒の待機を挟んで最大3回試行し、結果をJSONLへ逐次記録、終了時に集計JSONを保存します。中断後は同じコマンドで再開できます。
- `conversionMs` はPOST開始から全変換・R2保存完了までの実時間、`totalMs` はログイン・一覧走査を含みます。入力画像はクライアントへダウンロードせず、Cloudflare内でR2から変換サービスへ渡します。
- 本番反映時は本番Workerの更新と、対象URL・合言葉を本番用へ明示的に変更した補完処理が必要です。本番の既存画像には今回書き込みません。

Images bindingの変換は利用件数へ計上されます。画像を表示するたびには呼び出しません。現行のImages Freeは月5,000ユニーク変換までで、プランの上限・課金はアカウント全体の利用状況に依存します。

## 検証結果

2026年11月1日のdevelop独自ドメインで実測しました。

- 既存の写真相当JPEG400枚（3024×4032px、合計865,236,969 bytes）に対して、サムネイルは合計2,569,206 bytes（約2.57MB、平均約6.42KB/枚）。容量は99.7%減です。
- 初回処理は同時4件で82.4秒（一覧取得・ログインを含む）。370件が新規作成、1件が既存判定、29件が3試行後もHTTP 503でした。503の内部原因はこの計測では特定できていません。
- 失敗した1枚を手動で再実行して成功。その後、同時2件で400件を再走査し、28件を作成・372件をスキップ・失敗0件。再走査は39.9秒でした。開始から途中の確認・再実行を含む400件の最終完了まで153.5秒（約2分33秒）でした。「400枚を一度で82秒で成功した」という結果ではありません。
- 再試行に1秒・2秒の待機を追加し、スクリプトの既定並列数を2へ変更しました。
- その後、検索条件なしで検証環境の全生成キャラクター407件も走査し、残り7件を作成・400件をスキップ・失敗0件でした。本番データは未変更です。
- PC（1440×1000）・スマホ幅（390×844）の実管理画面で、写真400枚をスクロールして末尾まで表示。全800回の画像読み込みについてデコード成功、最大256px、元画像へのフォールバック要求0件、画像通信失敗0件を確認しました。この検証時のスクロール自動操作時間は表示速度の比較値には使っていません。
- 独立した2つのブラウザコンテキストでレーン設定も確認。管理画面は192×256pxのサムネイル、別コンテキストの `/game` 待機画面は3024×4032pxの元画像で表示され、確認後にテストのレーン設定を解除しました。以前の断続的な表示不具合の根本原因・解消まで証明する確認ではありません。
- 新規生成経路はMiniflare/workerd上の生成APIを通し、元画像・D1・WebPサムネイルが応答前に保存されることを確認しました。上流の画像生成APIはfixtureに置換しており、Geminiの実生成の所要時間は測っていません。

Chrome 156.0.8078.74、HTTP/3、同じ端末・同じオリジン・同じブラウザコンテキストで、最新12枚を並列に読み込み、画像が表示可能になる `img.decode()` 完了までを測定。元画像／サムネイルをAB/BA交互に各10バッチ（各120画像）、ブラウザHTTPキャッシュ無効・毎回別クエリで取得しました。最初の各1バッチは集計対象外。全要求がHTTP 200・ネットワーク転送ありで、回線の人工的な速度制限はありません。

| 指標 | 元画像 | サムネイル | 短縮率 |
| --- | ---: | ---: | ---: |
| 12枚すべての取得・デコード 中央値 | 5,987.5 ms | 209.3 ms | 96.5% |

画像の取得・デコード時間であり、管理画面全体の起動時間や実機スマホの計測ではありません。バッチ数は各10で、回線・端末・画像内容によって効果は変わります。CDN Cache APIは追加していません。

## 表示時間比較の再現

計測用Playwrightはアプリの依存関係とは別に準備できます。下記はMacのChromeを使う例です。

```bash
npm install --prefix .wrangler/browser-tools --no-package-lock playwright
PLAYWRIGHT_MODULE="file://$PWD/.wrangler/browser-tools/node_modules/playwright/index.mjs" \
CHROME_EXECUTABLE="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
node scripts/benchmark-character-thumbnails.mjs \
  https://animaldash-develop.logeek.tech outputs/thumbnail-display-benchmark.json
```

同じ最新12枚を同時にDOMへ追加し、全画像の `img.decode()` 完了までを測ります。元画像とサムネイルをAB/BA交互に各10バッチ、各120枚取得します。ブラウザのHTTPキャッシュをCDPで無効化し、各回のクエリも変えてデコード済み画像の再利用を避けます。最初の各1バッチは接続のウォームアップとして集計対象外です。全応答が200・ネットワーク転送ありであることを確認し、生データ・中央値・p95をJSONに出します。

この測定は管理画面と同じ画像APIを使う画像の取得・デコード比較で、管理画面全体のロード時間・LCPや実機スマホの性能を測るものではありません。回線速度を人工的に制限していません。

## 他端末での名前・一言の編集

キャラクター変更通知には対象IDと作成／編集の区分を含めます。読み込み済みの対象IDはレーン外でも情報を更新し、更新中の再配置は新しい情報の取得を待ちます。変更前に始まった応答はキャッシュへ反映しません。未表示・未参照のキャラクターをゲーム画面が一括取得する処理は追加しません。

検索中に編集通知を受けた管理画面は、検索条件を維持して先頭ページから再取得します。古いカーソルを保持して検索対象の追加・除外を取りこぼすことを防ぎます。新規作成時は従来どおり先頭ページを更新し、継続取得済みのページを保持します。元画像・サムネイルのURLや画素は変更しません。

この修正はdevelopの独立した2ブラウザコンテキストで確認しました。レーンから外した写真テスト400を別端末から改名・一言変更し、古い名前の検索結果から消えること、再配置後の `/game` に新しい名前・一言と元画像が表示されることを確認済みです。確認後はレーンから外し、名前・一言を元へ戻しました。Lint、通常／developビルド、138件のテストが成功しています。
